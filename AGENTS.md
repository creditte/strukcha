# Engineering rules

- `supabase/functions/_shared/relationship-policy.ts` (re-exported as `src/lib/relationshipPolicy.ts`) and its SQL twin `relationship_policy_evaluate()` are the only relationship rules, kept in step via `src/test/fixtures/relationship-policy-vectors.json` and `bun run test:sql` — one matrix stops browser, imports and database disagreeing. Browser inputs use it now; `src/lib/relationshipRules.ts` is a rule-free facade over it.
- Every XPM path (`sync-xpm`, `import-xpm`, `import-xpm-group`, preview `fetch-xpm-group`) decides relationships only through `_shared/xpm-policy-normalise.ts` and writes one evidence row per raw fact; sync/CSV call the bridge RPCs with `contract: 'canonical_v1'` and the job id as `import_run_id` — so retries never duplicate evidence and no path keeps its own label map.
- Unapplied/staged SQL lives in `supabase/pending-migrations/`, never `supabase/migrations/` — files there are treated as applied migrations.
- XPM group structures are identified only by `(tenant_id, structures.xpm_group_uuid)`; `_shared/xpm-group-reconcile.ts` plans and `xpm_apply_group_reconciliation` applies exact-key diffs for both sync-xpm and import-xpm-group, removing only `membership_source='xpm'` rows — so manual work is never wiped and same-name groups never collide. A same-name non-XPM diagram is never adopted automatically; it is linked only via user-confirmed `mode: "link"` (`xpm_link_existing_structure`, sets the group id only), never duplicated by default.
- XPM ownership figures pass through `_shared/xpm-ownership.ts` (zero → null, shares are units, never inferred %) and are only rewritten when `relationships.metadata_source` is XPM-managed — manual edits always win.
- Every backend-generated app link goes through `supabase/functions/_shared/frontend-url.ts` (FRONTEND_URL only if on its allow-list, else the canonical fallback; caller origins never reflected) — one place stops stale or attacker-supplied redirect addresses.
- Self sign-up never deletes or replaces an existing firm, account or invitation; `_shared/signup-guard.ts` decides create / resend-to-own-unverified-shell / silent, with DB-backed rate limits (`signup_rate_hit`) and one-time, attempt-limited codes (`signup_check_code`) — so repeat or hostile sign-ups cannot destroy data or reveal which emails exist.
- XPM clients whose business structure says "Sole Trader" are imported as `Individual` (`_shared/xpm-entity-type.ts`) — in XPM that client is the person, and person relationships (director, spouse, shareholder, trustee) must attach to them.
- "Open in Editor" for a group already linked by `xpm_group_uuid` navigates straight to the diagram (`src/lib/xpmOpen.ts`); the editor's `XpmUpdatesBanner` runs the write-free preview in the background and applies only after the same confirm dialog — so opening is never blocked on XPM reads. Stored "Sole Trader" XPM clients with no Trades As owner are retyped to Individual only through that confirmed apply (`xpmTypeCorrection`).
- Every `CREATE TABLE` in `public` carries its own `GRANT`s (service_role ALL; authenticated only the operations its RLS allows; anon only with a deliberate anon policy) in the same migration; `src/lib/migrationGrants.test.ts` (`bun run test:grants`) fails otherwise — since 30/10/2026 new tables get no automatic Data API access, so rebuilt schemas would break.
